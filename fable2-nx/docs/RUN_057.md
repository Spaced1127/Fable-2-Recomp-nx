# run-057 - name the invoked script function, make the upload probe report

Run 056 delivered the VM evidence and nothing from the upload probe. This run
closes the probe's silence and turns the crash from "a nil argument" into "which
script call, resolved from where".

## 1. What run 056 proved (from docs/runs/056/fable_2_056.log)

The VM probe worked exactly as designed:

```
22:14:31.111 [vm-call] #1 tid=7 caller=82228AF4 vm=507AAB88
            r4=4F7C3A70 r5=00000000 r6=50A97E44 r7=00000001
22:14:31.113 [vm-null] #1 tid=7 vm=507AAB88 index=1 elem=4F7C3A78
            type=00000000 value=00000000
            slot idx=1 elem=4F7C3A78 value=00000000 type=00000000 (0)
            slot idx=2 elem=4F7C3A80 value=00000000 type=00000001 (1)   bool false
            slot idx=3 elem=4F7C3A88 value=00000001 type=00000001 (1)   bool true
```

Read together with the guest code this is exact:

- arguments live at `[vm+12] + (index-1)*8`, each `{value @+0, type @+4}`;
  `[vm+8]` is the next free slot above them;
- **type 0 is nil and is also how the VM materialises a parameter the caller
  omitted** - the invoke helper fills missing parameters by writing `type = 0`
  and advancing `[vm+8]` (`0x82228918..0x82228934`);
- the crashing slot is **index 1**, the first argument, with `value = 0`,
  `type = 0`, i.e. a nil object where the binding expects a type-2 pointer (its
  `[value+0]` is read and passed to `sub_82227680`);
- the same binding was called twice in the same burst with a *valid* value
  (`idx=1 elem=4F7C3AC8 type=00000007 value=50C0A064`) and then once with nil,
  so the nil is one entry of a run of calls, not a permanent condition.

The caller `0x82228AF4` is the return address of a `bctrl` inside guest function
`0x82228830` (manifest alias `GuildChest_ProcessItem_82228830`, a name from the
earlier guild-chest work - the code is the **VM invoke helper**, not chest code):

```
[r4+4] == 6 ?  string callee -> named invocation
             : sub_82A2E400 (resolve value) -> prototype at [callee+16],
               param counts at +73/+74/+75, fill missing with type 0,
               dispatch through [[vm+20]+4] -> [+0] -> vtable[+16]
```

So the "native caller" of `sub_821C95D8` is the VM dispatcher itself: the nil was
**not** produced by a native lookup at that call site, it was already in the
script's argument frame. Which native call produced it is what this run watches.

## 2. Why the upload probe logged nothing, and the fix

The log has `deko3d: texture cache initialized` at 22:13:42.216 and no
`[upload-probe]` line at all, i.e. `RunUploadProbe()` was never called: the cvar
read false. Two causes were possible and the log could not tell them apart -
the flag defaulted to **false**, and nothing logged the gate. (The same run's
`deko3d_texture_upload = true` did take effect, so the toml *was* read; the
probe key was simply not in the file that was on the card.)

Fixed in the build:

- `deko3d_upload_probe` now **defaults to true**, so it runs even with the old
  toml still on the card;
- the gate logs itself either way:
  `[upload-probe] gate: cvar deko3d_upload_probe=true|false -> running the self-test|self-test skipped`;
- the five variants and their order are unchanged (control first, then the
  failing baseline, then one variable each).

## 3. What this run adds for the crash

- **`[vm-name]` / invoke ring**: guest `0x82228830` is hooked; every script
  invocation is recorded with its callee value and type, and the first twelve
  **named** invocations (type 6 = string callee) log their characters. A call to
  `'...arketExit_Gate'.` therefore appears by name.
- **`[vm-null] ... invoke #k`**: the failure dump now replays the last ten
  invocations with each callee's characters, newest last - the call that produced
  the nil is in that window.
- **`[vm-null] ... arg string idx=N`**: any argument slot whose type is 6 is
  printed as text, so the surrounding operands are named even when the failing
  one is nil.
- No guard and no skipped call: the run still ends at the fault. A guard here
  would hide whichever world/quest lookup is returning nil, and the PC oracle
  (same guest code, no crash) proves the value is host-dependent - so the fix has
  to be at the producer, and the producer is what these lines name.

## 4. The unifying hypothesis - what would confirm it

Hypothesis: the nil argument and the missing `Data\Worlds\Albion\` registration
share one producer, so fixing the world mount fixes both crashes.

State after run 056: **plausible, not proven.** For it:

- both symptoms are "a lookup by name comes back empty";
- both appear only on Switch, never on the PC oracle with identical guest code.

Against it:

- the two consumers are different data paths: the GUI key is a *resource path*
  (`Data\Worlds\Albion\`) used by the UI batch builder and checked with a
  liveness test (`0x82C63040` reads `[obj+8]` and a locked subobject), while the
  VM nil is a *script value* already sitting in an argument frame;
- nothing yet ties the marker/quest name seen in the crash registers to that
  resource registry.

The decision is made from this run's log, not before it:

- if `[vm-name]`/`invoke` shows the nil entered through a **named lookup that
  also misses** (the same name the GUI path wants, or a world/quest name whose
  registration is absent), the hypothesis holds and run-058 fixes the world
  registry producer;
- if the invocations show the nil arriving from a **script-visible call that
  returned nil for another reason**, run-058 fixes that producer instead;
- a guard stays off the table until one of those is named.
