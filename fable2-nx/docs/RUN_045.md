# run-045 - does the +0x64 writer run, and what does it store?

Run 044 named the class and the writer. `h=0x42538C10` is a **CECPlayerControl**
component (type descriptor `0x820A687C` = deleting destructor `0x8234E398` +
"CECPlayerControl"; constructor `sub_8234E2B0`; destructor `sub_8234E3E8`).
`+8` and `+0x64` are zeroed by the constructor. The only writer of `+0x64` is
**`sub_8234EC08`**, called from the update loop `sub_825F3050` (guest
`0x825F3538`): it releases the old object at `this+0x64` and stores a new
56-byte object built from the rect at `this+0x98..0xA4`.

This build hooks `sub_8234EC08` and logs, after every call, `self`, the rect and
the resulting `+0x64`. That separates the two remaining explanations:

- **ordering**: the writer never runs on this instance before the HUD draws it;
- **failure**: it runs on this instance and stores 0 (56-byte allocation or its
  constructor returned null).

## 5. Reading the result

- `[gui-writer] ... self=42538C10 ... +64=00000000` repeatedly: the write path
  runs but its 56-byte allocation/constructor fails → out-of-memory or allocator
  failure at that moment; fix allocator/memory, not ordering.
- `[gui-writer] ... self=42538C10 ... +64=<nonzero>` and the witness still sees
  `i=0`: something clears it between the update and the draw (release path).
- No `[gui-writer]` line with `self=42538C10` before the fault: the update loop
  never reaches this instance → ordering/condition; the fix is to run the update
  before the HUD draw (or make the draw wait for it).
- No fault: report how far it got.
