# run-064 - the present fence as the copy witness, and pixels either way

## 1. Run 063 in one paragraph

Rectangle lists are **fixed** (`[primitive] rectangle list #1..#8 drawn as a
triangle strip`, `primitive_type` skips 194 -> **0**), presents kept flowing (180 in
~10.3 s), and the present fence still signalled. But the per-copy fences never did
(`copy validation fence not signalled within 250 ms`, `texture staging fence not
signalled`), so **no readback was ever printed**, and the app died at ~10.3 s on a
`globals_textures.bnk` read right after uploading a 240x180 texture (upload #4).

## 2. Why a fence ring cannot be the fix

This deko3d has **no `dkFenceInitialize`**: `DkFence` is a plain struct that
`dkQueueSignalFence` re-arms on every submit. The presenter proves that: it
re-signals *one* fence object every frame and it reports every time. So "the fence
is one-shot / must be re-initialised" does not apply, and a ring of fences would
be the same struct in a different slot.

What differs is the **list content**: the fence that signals follows
`dkCmdBufCopyImage` (image -> image), and the fence that never signals follows
`dkCmdBufCopyBufferToImage` (buffer -> image). That is a property of the operation,
not of the fence.

## 3. What this build does about it

**(a) Present fence as the completion witness.** The queue is in order, so once
the present fence for a later frame has signalled, everything submitted before it
has executed. The presenter now counts those signals (`NoteFramePresented`, a
global present epoch), and the texture cache uses `PresentEpoch() >= submit + 2`
as the witness for both:

- **validation readback** - the chain is read back and **printed** when the witness
  fires (or its own fence, if it ever reports): checksum plus the first four
  pixels, `PASS` or `MISMATCH`, naming which witness was used;
- **staging retirement** - a block is freed when the witness says its copy is done
  (own fence polled first). Age 64 survives only as a last-resort bound.

The readback check also runs from `GetBoundTexture`, so it fires on draws, not only
on the next upload - a run with a single upload still prints its pixels.

**(b) The likely cause of a copy that never completes: cached staging.** Every
2D-engine operation that completes here reads or writes an *image*; every one that
hangs reads a **CPU-cached** staging block. `deko3d_upload_staging_uncached`
(default **true**) makes the DMA source a `CpuUncached | GpuCached` block, which is
write-through - no flush needed and no cache-coherence question for the 2D engine.
Set `false` to A/B the old cached staging.

**(c) The ~10 s death is now accounted for, not guessed.** Every upload logs its
dimensions, format, staging bytes and the remaining heap **before** the copy:

```
[upload] #4 240x180 format 7 -> deko 52 (737280 bytes staging, tiled 1, 1 layers)
[deko3d] texture upload: heap NNNN MiB untouched, process NN MiB unused of its pool
```

In run 063 the last upload before death was 240x180 (737 KB of staging) - far below
any 2D-size or heap limit, so a *limit* death is ruled out by arithmetic; the
remaining candidates are the copy itself and the 2 KB / 12-28 ms read storm on a
292 MB offset. The next log names both.

## 4. What the reply should be able to report

- `[upload-validate] PASS via present-fence witness: ... checksum XXXXXXXX, first
  pixels [5A5A5A5A 5A5A5A5A ...]` -> the copy path is correct and the white screen
  is purely a draw/geometry problem.
- `MISMATCH via present-fence witness: ... first pixels [00000000 ...]` -> the
  copy executed but landed nothing: the remaining variable is the destination
  image flags (texture images carry only `Usage2DEngine` while the presenter's
  carry `UsageRender | H2D | HwCompression`), and that is the next one-line test.
- No validation line at all -> the witness never advanced (presents stopped), and
  the last `[upload]` line plus its heap figure says why.
