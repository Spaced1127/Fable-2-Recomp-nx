# run-051 - the composed key, and where the 4 s goes

Run 050 named the gate but not the producer:

```
[gui-batch] bit #1 ret=00000000 k0=40102D60 '@.-p....... ....Data\Worlds\....'
[gui-batch] fn #1 -> 00000000, c=[0 x12]
[gui-batch] br #1 ret=00000000, c=[0 x12]
[gui-batch] exit #1 ... n12=0
(gate probe never fired)
```

The key dump started at the string **object**, so it showed the 16-byte header
and only the first 16 characters of the text. What is known for certain:

- the template is exactly `Data\Worlds\` (verified byte-for-byte in
  `default_image.bin` at `0x820A7810`: 12 chars, NUL-padded, one of 15 root
  names: `Data\TestWorlds\`, `Art\GUI\`, `Data\Art\GUI\Gameface\`, ...);
- `game_files\data\worlds` exists and `data\dir.manifest` lists it as
  `worlds\...` (lowercase); the key is `Data\Worlds\`. Case is **not** the
  likely cause - the Windows oracle (NTFS) and the Switch SD (exFAT/FAT32) both
  resolve case-insensitively, and this is a guest-side name lookup, not a file
  open (neither our log nor the PC oracle logs contain any `worlds` I/O);
- the 4.0 s is spent inside `sub_825F45A8` **before** the bit test, and that
  window has no I/O and no guest-thread log line at all; the GPU queue was
  already wedged 25 s earlier (upload stalled, present timeouts every 2 s).

So the producer is still unnamed, and a patch now would be speculative. This
probe closes the last two gaps in one run. It keeps every earlier hook.

## What is added

`[gui-key] enter` / `[gui-key] exit` wrap `sub_825F4310`, the key builder. It
has **exactly two call sites**, both inside `sub_825F45A8` (key 1 and the
fallback key 2), so these lines are unambiguous:

- `enter` logs the output slot, the manager, the static template slot
  (`0x8349750C` or `0x83497510`), the template pointer and the decoded
  template text, plus the three arguments.
- `exit` logs the string object the builder produced and **72 characters** of
  its text - the composed key, which run 050 truncated.
- The two timestamps bracket the builder: if `enter`/`exit` are milliseconds
  apart, the 4.0 s is in the container lookups that follow; if they are ~4 s
  apart, it is inside the builder itself.

Build: `90996B1B9FB5D1A67794E22526B0F0BDF9DE0BD6976C2960EAD647FE8F7394F6`,
tag `m1-probe-051`. Texture uploads stay on.

## Reading the result

- `[gui-key] exit ... chars='Data\Worlds\<something>'`: that is the exact key.
  If it names a world/level that exists under `data\worlds` in `game_files`,
  the registry entry is missing although the data exists -> producer defect. If
  it names something that does not exist anywhere on disc -> the request itself
  is wrong (asset name/id mismatch), and the fix is on that side.
- `enter`/`exit` ~4 s apart: the stall is inside the key builder; its args and
  the template it was given name the input that blocks.
- `enter`/`exit` milliseconds apart: the stall is in `Construct`/
  `IsNonZero`/`CheckAndExtractBit` after the builder; the key is still the
  decisive datum, and the next step is the container's insert side.
- Both keys failing (`tmpl=0x8349750C` then `0x83497510`) means neither the
  world root nor its fallback is registered.
