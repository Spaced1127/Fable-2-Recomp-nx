# run-066 - uploads ride the frame list (the submit that never executed)

## 1. What run 065 proved

```
a buffer->buffer:      fence TIMEOUT 250 ms; pre=AAAAAAAA post=[AAAAAAAA AAAAAAAA] FAIL
b buffer->image->buf:  fence TIMEOUT 250 ms; post=[AAAAAAAA AAAAAAAA] FAIL
c clear B to 0xC3:     fence TIMEOUT 250 ms; post=[AAAAAAAA ...] FAIL
d presenter image:     fence TIMEOUT 250 ms; inconclusive
```

Not one copy command executed - not even a plain **buffer -> buffer** copy, and not
even a **clear**. The readback buffers still hold the `0xAA` pre-fill, so the lists
never reached the GPU. Meanwhile frames keep being presented. That rules out
formats, units, flags, alignment, the 2D engine and the swapchain: **a list
submitted on the texture cache's standalone path is not executed**, while the
frame's own list is.

## 2. The two submit sites, and what differs

Both call `device_.queue()` (same handle) under the same `submit_mutex`, and both
use a `dk::Fence` local/member. What differs is **where the command list lives and
who submits it**:

| | present / frame list | texture upload (run 065 and earlier) |
|---|---|---|
| cmdbuf | the render-target cache's frame cmdbuf, opened by `BeginRecording()` | the texture cache's own `upload_command_buffer_` |
| memory | frame command memory, rotated by slot | `upload_command_memory_` (64 KiB), reused at offset 0 |
| submitted by | the command processor, once per frame, with the frame fence | the texture cache, on its own, mid-frame |
| result | executes | **never executes** |

Run 066 logs both sites with their addresses so the difference is on the record:

```
[submit] present site=presenter queue=0x... device=0x... fence=...
[submit] a buffer->buffer site=texture_cache standalone queue=0x... device=0x... fence=0x... cmdbuf=0x...
```

If the queue and device values match (they should), the conclusion is that the
standalone list is dropped between recording and submit - so the path is **deleted**
rather than repaired, per the finding.

## 3. The fix: uploads are recorded into the frame's list

`Deko3DCommandProcessor` now hands the texture cache a recorder
(`texture_cache_->set_frame_recorder(...)` returning
`render_target_cache_->BeginRecording()`), and every texture upload:

- records `copyBufferToImage` **and** the invalidate barrier into the **frame's**
  command list, before the draws that sample the image;
- submits nothing itself - the frame submit (whose fence demonstrably signals) is
  what executes the copy;
- retires its staging block against the **present epoch** (two frames later), so
  the block outlives the frame that reads it;
- logs `[upload] #N WxH recorded into the FRAME list (rowLength bytes, imageHeight
  rows)`.

The separate immediate-submit path survives only as the fallback when no recorder
is available (e.g. a command processor that has not opened a frame yet).

## 4. Acceptance checks in this build

1. **Frame-path pixel proof** - on the first frame-recorded upload, a 64x64 copy
   back from the uploaded image into a block pre-filled `0xAA` is recorded into the
   *same* frame list. Two presents later the bytes are logged:

```
[upload] probe armed: 64x64 of the first frame-path upload will be read back
[upload] frame-path readback: NON-ZERO first bytes [..] - the frame-recorded upload landed pixels
[upload] frame-path readback: still the 0xAA pre-fill ... - the frame-recorded copy still produced nothing
```

2. `[submit]` lines for both sites with queue/device/fence/cmdbuf addresses.
3. The old standalone diagnostic still runs, so the contrast is in one log: it
   fails while the frame path succeeds - or both fail, which would mean the frame
   list itself is not executing and the device/queue creation is the real target.

land, the white screen's remaining suspect is the present blit reading a guest
