# run-062 - boot ungated, validation in the frame loop, fence question asked on the render queue

## 1. What blocked run 061 (my regression, not a guest problem)

```
01:50:38.792 [core] presenter connected: 1280x720
01:50:39.496 [gpu]  [gpu-validate] step0 empty-list fence: TIMEOUT in 250 ms
01:50:39.831 [gpu]  [gpu-validate] step1 clear+fence: TIMEOUT in 250 ms
01:50:39.833 [gpu]  [upload-validate] submitting 64x64 chain: staging -> A -> B -> readback
01:50:39.955 [core] Initializing shader storage for title 4D5307F1...
<nothing, ever>
```

The chain submit is followed by `device_.WaitIdle()` - an **unbounded** queue
wait - and the queue never completed that list, so the command-processor thread
parked forever. That is exactly the failure `fence_wait.h` describes: no crash, no
violation, a live process, no frames.

- `rex_crash.log` is byte-identical to run 060's (`98A1A23D...`, 69110 bytes), so
  it carries **no** new fault information and is not evidence for anything here.
- The 250 ms `step0` timeout on an **empty list, before any copy existed** rules
  out "an earlier bad copy poisoned the queue" for that timeout - but it does not
  prove fences are broken either, because at that moment the queue had never run
  anything (and run 060 proved the queue *does* execute: it presented frames).

## 2. What this build changes

| item | run 061 | run 062 |
|------|---------|---------|
| boot validation | ran at texture-cache init, ended in `dkQueueWaitIdle` | **gone from boot**; the cvar is opt-in and defaults **false** |
| copy validation | synchronous round trip | submitted **inside the frame loop** with the first real texture upload, read back **by age** (8 submits), never waits |
| present fence | removed in 060 | signalled on the render queue after each present copy and **polled with timeout 0** every frame; logs either `SIGNALLED at present #N (M frames later)` or `NOT signalled after 60 presents` |
| boot logging | step names only | the texture-cache gate line prints the **queue handle** and states that present, upload and validation share that one queue |
| blocking waits | one (fatal) | **none** anywhere in the boot or frame path |

(The `deko3d_upload_validate` cvar remains available for a later shape experiment,
but it is a frame-loop diagnostic now, never a boot gate.)

## 3. What the log will answer, in order

1. `[upload-validate] gate: deko3d_upload_validate=...; queue handle 0x...` - the
   queue identity, before anything is submitted.
2. `[present] #N slot=S branch=B guest#E age=A ...` again from the first frame,
   like run 060 (which presented for 10 s).
3. `[present-fence] SIGNALLED on the render queue at present #N (M frames after
   the copy was submitted)` - **the fence question answered on the queue that
   demonstrably executes**. Then fences are usable for retirement again.
   `NOT signalled after 60 presents` - the queue executes but the primitive does
   not report it, and age-based retirement stays the only mechanism.
4. When the first real texture uploads (usually ~10 s in):
   `[upload-validate] submitted 64x64 chain in-frame (no wait)` and, ~8 submits
   later, `PASS: 64x64 chain byte-identical` or `MISMATCH ... src=5A rb=00`.
   The chain is staging -> A (`copyBufferToImage`, rowLength 4096 **bytes**,
   imageHeight 64 **rows**) -> B (`copyImage`, the presenter's API) -> readback.
