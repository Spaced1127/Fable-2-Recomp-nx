# run-055 - Horizon socket service (new null class) + status of the presenter

## 1. The page-set crash class is closed

Run 054: every guard held (`sub_822358A8` #1/#2, element #1, clip #1/#2/#3) and
`read of guest 0x00000024` never recurred. Survivability rose ~45 s -> ~50 s.

## 2. New fault: `read of guest 0x00000000`, network init

Crash block `A11477CC...`, faulting function **`sub_821C95D8 + 0xD8`**
(`pc`/`lr` agree this time), `far = 0`, `instruccion 0xb8606a80`, `x0 = 0`.

The line immediately before it:

```
[svr2011] net: socket(2, 1, 0) failed: 10022
```

Mechanism: `NetDll_socket_entry` (`sdk/src/kernel/xam/xam_net.cpp:855`) creates
an `XSocket` and calls `XSocket::Initialize`, which calls the raw POSIX
`socket(af, type, proto)` (`sdk/src/system/xsocket.cpp:59`). On Horizon the BSD
service must be brought up first (`socketInitializeDefault`); nothing in the
port ever did, so `socket()` fails with `EINVAL`, the HLE returns -1 with
`WSAEINVAL` (10022), and the guest's online init dereferences the socket it
never got.

### Fix

`XSocket::Initialize` now performs a one-time `socketInitializeDefault()` under
`__SWITCH__` (lazy `std::call_once`, logged as
`[socket] Horizon BSD service initialised`) and retries the `socket()` call
once. No other platform changes; no guest memory is touched. If the service
still cannot start, the old -1/WSAEINVAL path is unchanged and the log names the
`Result`.

## 3. Presenter: what actually lands

From run 054's log:

```
21:42:24.776 [present] branch=4 ...            -> swap 0: presented (placeholder)
21:42:25.085 [present] branch=1 target=1280x2048 guest=1280x720
21:42:25.088 deko3d: swap 1: presented (guest output)
21:42:25.114 deko3d: swap 2: presented (guest output)
21:42:41.860 giving up on render recording; the last frame presented stays on screen
21:42:43.867 present copy fence timed out ... presenting anyway (#1)
```

So the guest output **is** attached and two real guest frames were presented
before the queue wedged (~16 s in). After `giving up on render recording` the
presenter keeps cycling but every copy times out - the last good frame stays up.
The white screen is therefore the M0 queue wedge, not a wrong source image.
With run-054's present-on-timeout the screen no longer freezes at frame 0; it
shows whatever last landed and updates when the queue lives.

## 4. Display: still gated by the upload wedge (not fixed here)

User: white since deko3d was introduced. The presenter is not at fault - run 054
proved `branch=1 target=1280x2048 guest=1280x720` and swaps 1/2 presented as
guest output. The first texture upload's `copyBufferToImage`
(`texture_cache.cpp:406`) never completes, its 5 s fence times out, uploads are
disabled and the device queue is dead from then on: the frame record fence times
out (`giving up on render recording` ~17 s) and every later present copy times
out. Every present path (image copy, buffer->image, CPU upload + copy) is GPU
work on that queue, so no display path survives it. Run-056 should isolate the
hang with a 64x64 one-shot self-test (variants: no in-list barrier,
`CpuUncached` staging, untiled destination).
