## The decisive re-read: the exit() block is STALE

`rex_crash.log` has been **69110 bytes, hash `98A1A23D`, since run 058** - every
run 059-070 returned it byte-identical. The crash logger
(`exception_handler_switch.cpp`) APPENDS one block per boot via the fs service,
with no dedup; the file grew one block per run through 050-058. Therefore:

- The `==== exit() fuera del cierre ordenado ====` block was written by run
  **057 or 058**, not by the recent runs.
- Runs 059-070 fired **NO hook at all** - not exit(), not abort(), not
  std::terminate, not a CPU data abort. The current death is a **silent
  OS-level kill** (GPU channel fault is the prime candidate) or a direct
  svcExitProcess - NOT the exit() the old block describes.

Symbolising the old offsets against the CURRENT ELF is invalid (the layout
shifted since 058); approximately, the app frames land in guest recomp code
(`sub_82B30878`, the VM dispatcher `ProcessAndProcessAndProcess360_82BF2470`,
`sub_82489E08`) - the OLD exit was guest-triggered through an HLE call. The only
exit() sites in the SDK are `XamShowDirtyDiscErrorUI` (exit(1), the guest's
disc-read-error path) and `HalReturnToFirmware` (exit(0)); both log ERROR first,
and neither line appears in any recent log - consistent with the block being
stale. A fresh capture is required for exact names.

## What this build instruments (no GPU behaviour change)

1. **Per-boot marker file** `logs/rex/rex_exit_marker.log`: every exit/abort/
   terminate/data-abort hook writes `build=... reason=... hilo=... tick=...`
   FIRST (fs service, no stdio locks). Empty/absent after a death = no hook
   fired = OS kill. Present = the hook fired and the reason is named.
2. **Build tag in every crash block** (`build: m1-f1-071`) - stale blocks can
   never again be mistaken for the current death.
3. **Last-host-action ring** (16 entries, lock-free) dumped into every crash
   block, plus a per-line-flushed `logs/rex/rex_actions.log` for low-rate
   events: upload start/record/depth-skip, probe arm, IO read failures,
   XamShowDirtyDiscErrorUI, HalReturnToFirmware, GPU error. Per-frame events
   (present, frame submit) go to the ring only.
4. **GPU error-state witness**: the presenter checks `dkQueueIsInErrorState`
   every present; on the first true it logs `[gpu-error] queue in ERROR state
   at present #N - GPU channel faulted; OS kill expected`. The death-watch line
   also prints the error state. This turns the silent GPU-fault death into a
   named log line.
5. **IO read failures logged**: `[io] READ SHORT/FAILED '<path>' off=... req=...
   got=... status=...` (first 64) - the trigger chain for the guest's
   dirty-disc exit, if that path is ever reached.
6. **Probe opt-out cvar** `deko3d_upload_probe_frame` (default true): a later
   run can discriminate the probe readback from the upload copies without a
   rebuild.

Kept from 070: staging cohorts (fence-witnessed, never age), depth skip,
guest-readback #30/#150, drew/skipped census, skip-census, death-watch.

## Acceptance / how to read the result

- **`[gpu-error]` line present** -> GPU channel fault confirmed; the fatal list
  is the frame named by the last `[frame] submit #N carried U copies` and the
  action ring; next run discriminates its members (probe cvar, then formats).
- **rex_exit_marker.log has a new `build=m1-f1-071` entry** -> a hook fired;
  the crash block now carries the build tag, the exact stack (symbolise against
  THIS build's ELF: NRO offset = ELF vaddr, identity map) and the action ring;
  the reason (exception type / assert / exit site) is named. Fix belongs there.
- **Neither** -> direct svcExitProcess or an OS kill with no channel error;
  the action ring + rex_actions.log tail still name the last host action.
