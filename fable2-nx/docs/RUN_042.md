# run-042 - is the draw path the killer?

Run 041's user observation is decisive: the app **died by itself** at the ~9 s
log terminus, with no `rex_crash.log` block, no guest violation and no witness.
The SDK reports host memory faults and `exit()`/`abort()`; none fired. The death
is below the guest layer - an OS kill, a GPU channel fault, or a fatal path that
never reaches the reporter. It is not the known `0x24` null-deref.

This run isolates the most likely layer. Every draw is skipped before it touches
a ring or command list, while clears, copies, resolves and presents still run.
If the app survives past 9 s, the death is in the draw path. If it still dies at
9 s, the draw is exonerated and the next variable is the present/copy path.

The build also logs a `[gpu-wait] stuck ...` line if a PM4 wait stays unmatched
for 2 s (the other candidate mechanism), and the null witness stays armed.

Build: SHA-256 `B14BC4F76098EBE3816CE99F69277184A259EEFAF161C55BE7C9B321F228BA6B`.

## 5. What the result means

Near the top of the log:

```
[fable2] build tag: m1-witness-042 (witness + gpu-wait + draw isolation switch)
```

Then the switch must show effect (the first few draws):

```
deko3d: draw skipped (diagnostic_skip_draws) - occurrence 1
```

- **Survives past 9 s** (menu quiet, no death): the draw path is the killer.
  The next run re-enables draws and logs their state to find the fatal one.
- **Dies at ~9 s** with `diagnostic_skip_draws` lines: the draw is exonerated.
  The death is in the present/copy path or an OS kill; the screen message and
  whether a `[gpu-wait]` line appears will separate those.
- **`[gpu-wait] stuck 2.0s on mem|reg 0x...`** names the unmatched PM4 wait (the
  other candidate). If it appears and the app dies, that wait is the gate.
- If a `[gui-witness]` line appears, the fault fired; return the log at once.
