# run-068 - does that one copy execute? A synchronous answer that cannot lie

## 1. Why run 067's verdict was not accepted

Run 067 submitted only the 960x720 copy and its fence timed out after 1000 ms - yet
the same queue then presented 180 frames and the present fence signalled at
present #1. A submission that "hangs" for a second while everything after it runs
normally is far more consistent with **the copy submission never being executed**
than with a wedged 2D engine. The summary line ("the copy alone is the killer") was
therefore premature and is retracted.

## 2. What this build does: stop trusting the fence

At setup only, for each of three `DkCopyBuf` descriptors:

1. record the copy into a **fresh list**, and log the **list handle**, the
   **command buffer it came from** and the **source GPU address/pitch** - i.e. what
   was recorded, from where, before submitting;
2. submit it, log the fence state (`wait(0)`) **before** and **after** a
   `dkQueueWaitIdle` that runs in a thread with a 2 s observation window (the API
   has no timeout of its own, so the window is ours and the log always continues);
3. read 64x64 of the destination back and print the pixels;
4. verdict **EXECUTED** (pattern read back) / **DROPPED** (WaitIdle returned, the
   destination is untouched) / **WEDGED** (WaitIdle never returned).

Descriptors tried, because the header documents no units for them:

| attempt | rowLength | imageHeight | what it represents |
|---|---|---|---|
| A | 4096 | 720 | rows - what the port passes now |
| B | 4096 | 2949120 | total bytes - the old reading |
| C | 0 | 0 | tightly packed, 3840-byte rows - the form deko3d's own samples pass |

## 3. The units check, as far as it can be settled off-console

- The installed `deko3d.h` gives **no** comment on units.
- deko3d's own samples (e.g. Connectome/Drasilia's `copy_buffer_to_image`) pass
  `rowLength: 0, imageHeight: 0` with a tightly packed scratch buffer.
- `DkCopyBuf` is Vulkan's `VkBufferImageCopy` buffer pair, whose spec says
  `bufferRowLength`/`bufferImageHeight` "specify in texels a subregion ... If either
  of these values are zero, ... tightly packed".

So **rows** is the consistent reading, and 0/0 is the canonical tight form. Attempt
C therefore tests the shape that cannot depend on the interpretation at all: if C
works and A does not, the port's padded-pitch descriptor is wrong; if A and C both
work, the earlier failures were the dead submission path, not the units.

## 4. What each outcome means

- **EXECUTED on A and/or C** -> the copy is legal. Run 066's ~250 ms death is then
  the draw that samples the uploaded image, and run-069 bisects the
  descriptor/sampler path.
- **DROPPED on all three** -> the command never reaches the GPU even though
  `WaitIdle` returns: the list/submit pairing or the command memory is being
  discarded, and the next step is to record the copy into the *frame* list only
  (already done) and check `[submit]` addresses from run 066's log.
- **WEDGED on any attempt** -> a real wedge, and only then is copy legality (flags,
  tiling, tile-aligned rect) the thing to pursue - with the attempt's own line
  naming which descriptor wedged.

Nothing else changes in this build: guest path, present blit and UI untouched, and
the frame-loop probes stay off (`deko3d_copy_bisect = false` now).
