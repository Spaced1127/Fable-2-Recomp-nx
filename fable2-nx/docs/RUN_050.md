# run-050 - why is the UI batch empty?

Run 049 settled the branch question and confirmed the static prediction: the
component update **does** reach the pass.

```
22.413  [gui-mark] pass #1 self=42220210 w36=40537DC0 mgr=404BC8A0
        n24=40537DC0 h2=42538C10 loop=00000000 r3=40558D98 w3_36=40558DC8
22.417  [gui-pass] #1 self=404BC8A0            <- the pass call, 4 ms later
26.527  [gui-upd] #1 ... h2=42538C10 h2+64=00000000   <- pass returned 4.1 s later
26.656  [gui-witness] ... h=42538C10 w64=00000000     <- draw faults 130 ms after
```

`wait` never fired, so the `[0x834BE654]` loop is not involved. The pass was
entered with the faulting control (`h2=42538C10`) and returned after 4.1 s with
`+0x64` still 0. Static reading of `sub_825F3050` says it builds a UI batch by
calling `sub_825F45A8` and jumps to its cleanup path (`loc_825F389C`) when that
returns 0, skipping every batch list and the writer at `0x825F3538`. That is the
only non-crashing path consistent with the 049 log.

This build logs the deciding values. No behaviour changes, reads only.

## What is added

| hook | address | logs |
|------|---------|------|
| `[gui-batch] fn` | `sub_825F45A8` entry | manager, args, host, out struct, **return value**, the twelve batch vector counts |
| `[gui-batch] br` | `0x825F3208` (just after the call) | the deciding byte in `r3` + all twelve counts from the pass frame |
| `[gui-batch] exit` | `0x825F389C` (early-exit target) | the vector bases still live at the exit |
| `[gui-batch] bit` | `0x825F4668` (inside `sub_825F45A8`) | the one bit test that can produce a 0 return, plus the two static key strings at `0x8349750C`/`0x83497510` and the stack key |
| `[gui-batch] gate` | `0x825F3510` (writer gate) | hash + wrapper/control chain - only reached if the theory is wrong |

All run-049 hooks (witness, `[gui-upd]`, `[gui-pass]`, `[gui-writer]`,
`[gui-state]`, `[gui-mark]`) stay on. Texture uploads stay **on** to reach the
fault.

## Reading the result

- `[gui-batch] fn ... -> 00000000` and `[gui-batch] br ... ret=00000000` with
  all twelve counts 0: confirms the empty batch. `[gui-batch] bit ret=00000000`
  then names the gate: the bit test on the key string is false.
- `[gui-batch] bit ret=00000001`: the batch builder was not the blocker; read
  the twelve counts in `[gui-batch] fn` - the empty list(s) name which producer
  is missing.
- `[gui-batch] gate` firing at all: the theory is wrong; the hash/`c180` pair
  shows why the compare failed (and the run would fault on guest 0x4 if the
  else branch were taken, which has never happened).
- The `'...'` fields are the decoded key strings; they name the flag table the
  bit comes from.
