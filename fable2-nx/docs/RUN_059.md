# run-059 - every fence wait removed, and the name table watched

Run 058 settled the primitive and confirmed the upload fix; one wait was left and
it froze the screen again.

## 1. What run 058 proved (docs/runs/058/fable_2_058.log)

```
22:28:11.257 [upload-probe] fence-only:  TIMEOUT in 1000 ms (queue error state 0)
22:28:12.259 [upload-probe] clear-only:  TIMEOUT in 1000 ms
22:28:16.273 [upload-probe] summary: ... the FENCE is the problem: dkFenceWait never
             observed a signal for work that the queue demonstrably completed
22:28:23.608 deko3d: uploaded texture 2D (960x720, format 23) without a fence wait;
             1 staging block(s) in flight
22:28:23.930 deko3d: fence wait timed out for previous frame's render list after 250 ms
22:28:23.933 giving up on render recording; the last frame presented stays on screen
```

- **The fence primitive is dead on this stack.** `fence-only` signals a fence on an
  **empty** command list and still times out, so no `dkFenceWait` can ever be
  trusted - not for copies, not for clears, not for an empty list.
- **The upload fix works**: the 960x720 texture was submitted with no wait.
- **The remaining wait is the resolve/render-list one**: 250 ms after the upload,
  `EnsureRecording` polled the previous list, failed, and set
  `rendering_stopped_` - which is the `giving up on render recording` freeze.

## 2. What this build changes

**All camera-facing waits removed** (`PollFence` in `fence_wait.h` polls once with
a zero timeout and never blocks, never stops recording):

| site | before | now |
|------|--------|-----|
| presenter, present-copy fence | 2 s wait, present anyway | fence removed entirely; copy + present submitted back to back |
| `EnsureRecording`, previous frame's list | 250 ms wait, then **stop recording** | poll, then continue - recording is never abandoned |
| `WaitForPendingList` (draw path) | 250 ms wait, skip the draw, stop recording | poll, continue; no draw is skipped for a fence |
| `SubmitAndWaitForReuse` (mid-frame split) | 250 ms wait, stop recording | poll, continue |
| texture upload | 5 s wait | already fence-free (`deko3d_upload_no_wait`) |

The upload self-test now defaults **off** (`deko3d_upload_probe = false`): its
verdict is recorded and its seven 1-second bounds only delayed boot.

**Per-present telemetry** (`[present]`, one line per presented frame):

```
[present] #N slot=S branch=B guest#E age=A since_refresh=Tms WxH
```

- `branch` 1 = guest render-target image, 2 = GPU pixels, 3 = CPU pixels,
  4 = pattern only (no guest output attached);
- `guest#E` counts guest-output refreshes, `age` counts presents since the last
  refresh (0 = this frame carries a fresh guest image), `since_refresh` is
  wall-clock age in ms.

That is the "does the display follow the guest?" measurement: a run of
`age=0` with `guest#` climbing means each guest frame reaches the swapchain; an
`age` that keeps climbing means the presenter is re-presenting a stale image.

## 3. What should be on screen

If the picture follows the guest frames, the screen stops being a frozen white
placeholder and starts changing at the menu's 30 Hz: the boot/logo frames, then
the menu background as the guest draws it. Texture uploads now complete without
stalling, so the menu art may also appear for the first time (M3's first real
evidence). If the screen still does not move, the log now says exactly which
branch feeds the swapchain and how old it is, and there is no "giving up on render
recording" line left to blame.

## 4. The name table (crash side)

New hook on the engine's **name-table lookup, guest `0x82C64018`** - the function
the GUI batch builder calls with the composed key `Data\Worlds\Albion\` before its
liveness test at `0x82C63040`. Every call logs:

```
[vm-lookup] #N caller=XXXXXXXX key=XXXXXXXX '<text>' found0=XXXXXXXX found8=XXXXXXXX
```

- `caller` distinguishes subsystems: `825F4660` is the GUI batch builder; any
  other caller with an entity-looking key says entities share this table.
- `'<text>'` is the requested key (characters at key object `+16`, the layout this
  class uses).
- `found0` / `found8` are the resolved object (`0` = miss).

At the fault the same ring is replayed as `[vm-null] ... [vm-lookup] #k`, next to
the invoke and callee rings, so the miss is read with the call that used it.

This is the direct test of the host-side finding from run 058: the missing
argument is the entity **`BowerstoneMarketExit_Gate` (`0xE6CCB784`)**, and both it
and `Data\Worlds\Albion\` are lookups into the Albion world.

- Table populated but this key `found=0` -> a registration bug (the world's
  entries are there, this one was never added): fix at the entity registration.
- Every world key `found=0` -> the mount never ran: fix at the mount producer.
- `BowerstoneMarketExit_Gate` never appears -> entities use a different table, and
  the log's `caller` values say which one to hook next.
