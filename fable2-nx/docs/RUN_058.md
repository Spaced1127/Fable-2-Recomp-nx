# run-058 - fence-free texture upload, and a name probe that cannot guess wrong

Run 057 produced two verdicts and one fact that changes the upload diagnosis.

## 1. What run 057 proved (docs/runs/057/fable_2_057.log)

Probe, now reporting:

```
23:56:56.222 [upload-probe] gate: cvar deko3d_upload_probe=true -> running the self-test
23:56:58.231 [upload-probe] control-presenter-flags: TIMEOUT in 2000 ms
             (flags D04, staging cached, barrier yes, flush yes, queue error state 0)
23:56:58.233 [upload-probe] baseline-2dengine: skipped (queue dead ...)
             ... all remaining variants skipped
```

and, decisively, the renderer right afterwards:

```
23:56:58.386 frame 0 drew 0 ...   swap 0 presented (placeholder)
23:56:58.619 frame 1 drew 0 ...   swap 1 presented (guest output)
23:57:03.524 frame 127 drew 0 ... (nothing stalled)
```

So the 64x64 copy **did not stop the queue** - 127 frames were recorded after its
fence was declared lost. The presenter never waits on that fence either: it
submits the copy, presents immediately, and only looks at the fence on the next
frame, with a bound, and proceeds anyway.

**Conclusion:** `dkFenceWait` does not observe a signal for these 2D-engine
copies on this stack, and the 5 s bounded wait is itself what stalls the command
processor for five seconds per texture, which is what freezes the display. The
copy path may be fine; the *waiting protocol* is not.

Corollary: the old probe design was wrong in the same way - it treated one lost
fence as a dead queue and threw away every other data point.

VM name capture: also wrong. The twelve `[vm-name]` lines printed `'PP.4......'`,
`'CI32Vector2'` (a type name), `'sh...'` - the text is **not** at `[value+0]` or
`[value+16]`, so the offset was a guess and it produced noise. The `[vm-null]`
evidence is unchanged and still exact: `index=1 type=00000000 value=00000000`.

## 2. Upload fix: submit like the presenter, never wait

`deko3d_upload_no_wait` (default **true**) replaces the 5 s wait:

- the copy is submitted and the function returns immediately - no fence wait;
- **correctness does not depend on the wait**: the copy and every draw that
  samples the image are on the same queue, so queue order already puts the copy
  first. Only the *staging block's lifetime* needs the fence.
- staging blocks are therefore kept in a small list; on each later upload their
  fences are **polled with a zero timeout** and the blocks whose copy completed
  are freed. If fences never signal, the list grows to 64 blocks (one per
  texture, staging-sized) and then uploads stop with one clear line - bounded, so
  a session cannot exhaust memory;
- `deko3d_upload_no_wait = false` restores the old bounded wait for A/B.

This is the presenter's own protocol, scaled to textures: it is the only protocol
this port has already run for thousands of frames without stalling.

### The same lost signal at the other waits

The upload is not the only place that blocked on one of these fences: the
render-target resolve path (`WaitForPendingList`) waits up to 5 s on
`resolve_fence_` before a frame that needs the ring, and that wait is what
produced run 057's `fence wait timed out for previous frame's render list`
followed by `giving up on render recording`. The same lost signal, a second
freeze.

So `deko3d_fence_wait_ms` (default **250**) now bounds every `WaitFence`. A
healthy GPU completes this work in microseconds, so 250 ms never trips; a lost
signal costs a hiccup instead of a five-second freeze. It is one diagnosis with
two call sites, and both are switchable for A/B (`deko3d_upload_no_wait`,
`deko3d_fence_wait_ms = 5000`).

## 3. Probe redesign (so one lost fence cannot hide four answers)

The self-test now runs **four controls first**, then every copy shape, and never
skips:

| # | variant | what it isolates |
|---|---------|------------------|
| 1 | `fence-only` | an empty list plus `signalFence` - if this times out, `dkFenceWait` is broken and no copy verdict means anything |
| 2 | `clear-only` | a render-target clear plus the same fence - is it copies specifically, or any GPU work? |
| 3 | `control-presenter-flags` | the presenter's image creation, 64x64 |
| 4 | `baseline-2dengine` | today's texture image creation |
| 5 | `staging-cpuuncached` | uncached staging |
| 6 | `dest-pitchlinear` | untiled destination |
| 7 | `no-inlist-barrier` | barrier removed |

Each is bound to 1 s, all are attempted, and the run ends with one summary line
that states which reading applies.

## 4. VM name extraction (no more guessed offsets)

`NameCandidates()` prints, for each object:

```
[vm-name] callee #N obj=XXXXXXXX words W0 W1 W2 W3 W4 W5
[vm-name]   inline +0 '...' +4 '...' +8 '...' +C '...' +10 '...'
[vm-name]   via [+0]=XXXXXXXX '...' | +10 '...'      (and +4, +8)
```

i.e. the raw six words, the text at five inline offsets, and the text behind each
of the first three pointer words. Whichever line holds real text names it, and
the raw words identify the layout for good.

Two rings feed it: a 16-deep ring of **type-6 (named) callees only** - so hundreds
of ordinary calls cannot crowd out the ones near the fault - and the 10-deep
all-invocation ring. Both are replayed by `[vm-null]` at the moment of the fault,
with the type-6 ring printed through `NameCandidates`.

## Reading the result

Upload:

- `[upload-probe] fence-only: PASS|TIMEOUT` - if TIMEOUT, `dkFenceWait` is broken
  on this stack and the fix direction is confirmed: never wait, always poll.
- `[upload-probe] clear-only: ...` - separates "copies" from "any work".
- `[upload-probe] summary: ...` - the summary line states the reading.
- `deko3d: uploaded texture ... without a fence wait; N staging block(s) in
  flight` - the new path running. N staying small means the fences do signal and
  are being harvested; N climbing to 64 means they do not.
- **No** `fence wait timed out for texture upload` and **no** `giving up on
  render recording` = the stall is gone. If a timeout still appears, read its
  elapsed ms: with `deko3d_fence_wait_ms = 250` it must be ~250, and the next
  step (run 059) is to make that particular wait non-blocking as well.
- Texture uploads that keep coming (`[upload-probe]`/upload lines across many
  frames) = the display path is alive.

Crash (unchanged site, still unguarded):

- `[vm-name] callee #N obj=... words ...` and the `inline`/`via` lines - one of
  those strings is the script name. Send the log even if it crashes at 47 s; the
