# run-063 - rectangle lists drawn, fences restored, readback pixels

## 1. What run 062 settled

```
[present-fence] SIGNALLED on the render queue at present #1 (1 frame(s) after the
                copy was submitted) - fences work on this queue
```

**Fences work.** The port's "fences never signal on this stack" note was wrong and
has been **deleted from the code and the docs** (`fence_wait.h`, `fence_wait.cpp`,
`render_target_cache.cpp`, `texture_cache.cpp`). What is still true, and is the
part worth keeping: every wait must be **bounded and named**, because waiting on a
queue that is not executing stops the command processor and the game with it.
Run 062 also still died at ~9.5 s on a `gui_textures.bnk` read with the unchanged
crash block (`98A1A23D...`), so that death is still unexplained - and the age-based
staging retirement is now its prime suspect, because a 960x720 block could be
retired while its copy was still in flight.

## 2. The "quad primitive" is actually a rectangle list

The skip says `host primitive 8 has no deko3d equivalent`. Primitive 8 in the
xenos enum is **`kRectangleList` (0x08)**, not a quad strip: `kQuadList` is 0x0D
and `kQuadStrip` is 0x0E, and `GetDkPrimitive` already maps both. So the missing
case was `kRectangleList`, and the converter was never at fault.

A rectangle list supplies four corners per rectangle in TL, BL, TR, BR order -
which is exactly a two-triangle strip - so it is drawn now with the existing index
path and **no shader change**:

```
case xenos::PrimitiveType::kRectangleList:
  return DkPrimitive_TriangleStrip;
```

and every such draw is counted:

```
[primitive] rectangle list #1 drawn as a triangle strip (4 corners = 2 triangles per rectangle)
```

The 3-vertex rectangle-list form D3D9 uses for resolves degenerates to one
triangle; this backend does not implement the resolve trick, so that is a no-op.
194 UI draws per run now reach deko3d instead of the skip sink - that is the class
that leaves a menu as flat clear colour.

If the rectangles arrive with the opposite winding for this guest's cull mode,
that is a one-line follow-up (swap two indices or flip the cull mode for the
draw), and the counter makes it obvious whether they are being drawn at all.

## 3. Fences restored where they matter

| site | run 062 | run 063 |
|------|---------|---------|
| present copy completion | poll only (telemetry) | **bounded 250 ms wait**, named, then present regardless |
| texture staging retirement | age (8 submits) only | **bounded 250 ms wait** on the copy's own fence; age (24) only as fallback |
| copy validation readback | age only | its fence (bounded 250 ms) or age 4 |

`FencesObserved()`/`NoteFenceObserved()` record that a fence really did signal, so
the fallback is only used when the primitive has not been seen to work - never
because of a stale assumption.

## 4. The readback now logs pixels

`deko3d_upload_validate` is **on** again (in-frame, non-blocking: submitted with
the first real texture, checked on a later upload):

```
[upload-validate] submitted 64x64 chain in-frame (no wait): staging -> A -> B (present blit) -> readback, pitch 4096 B, 64 rows, flush yes
[upload-validate] PASS: 64x64 chain byte-identical (fence signalled), first pixels [5A5A5A5A 5A5A5A5A ...] - the upload shape AND the present blit both land pixels
[upload-validate] MISMATCH (fence signalled): N samples differ ...; first pixels [00000000 ...]
```

That is the proof we have been chasing, in bytes rather than in a fence verdict.
