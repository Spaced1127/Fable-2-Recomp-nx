# run-054 - clip choke-point guard + what the presenter actually shows

Two items, one of which changes the crash path.

## 1. Crash: guard the one choke point, not a consumer

Run 053 guarded `sub_82426ED8` (the element rect/blit) and the fault still
fired 3 ms later, same instruction, same `far = 0x24`.

- The site is `sub_82265A80` reached from **`sub_822659E8`**, which has ~75
  callers - guarding callers cannot converge.
- `sub_822659E8` itself does `addi r4, r5, 36` for the clip rect, so **r5 == 0
  dereferences guest 0x24 for every caller**.

That is the choke point every element draw passes through: no clip rect means
nothing to clip, so the call is skipped and the caller's output rect is zeroed
(an empty rect draws nothing). Both earlier guards stay.

## 2. Presenter: why the screen is white (root cause found)

`PaintAndPresentImpl` presents in four ways: 1 = guest render-target image
(copyImage into the swapchain slot), 2 = GPU pixels (copyBufferToImage),
3 = CPU pixels (memcpy + upload), 4 = pattern only (no guest output).

The present copy signals `copy_fence`; the **next** frame waits on it for 2 s.
In every run since 030 the wait times out (`present copy fence timed out`,
queue error state 0) and the code returned `kNotPresented` - so
`presentImage` was **never called again after the first frame**. The display
keeps the first swapchain image, which is the cleared/pattern image: white,
forever, while the guest keeps rendering correctly into its own target (which
is what the EFB dumps show).

The copy never completes because the deko3d queue is already wedged by the
texture upload (M0): same root as the 4 s stalls.

Changes (diagnostic + one behaviour change):
- one line per branch change: `[present] branch=... target=... gpu=... guest=...`
  so the log proves whether guest output was attached at all (branch 4 = it was
  not, and no fix below the presenter can help);
- on copy-fence timeout the presenter now **presents the slot anyway** instead
  of freezing on frame 0. It cannot be worse than a frozen image, and it makes
  the screen follow new frames the moment the queue lives.
