# run-044 - name the class of the null GUI field

Run 043 captured the M1 provenance: the app survives to 43 s with texture uploads
enabled, the witness fires on `sub_822358A8` with `r3=0`, caller `0x82390590`,
and the chain ends in the live object `h=0x42538C10` whose `+0x64` field is 0.
The guest violation follows. The remaining unknown is **which class `h` is**, so
that its `+0x64` writer can be found and fixed.

This build extends the witness, at the same point, to dump:

- `h`'s vtable (`[h]`) and the page fields it uses (`+8` table, `+36/+40` origin,
  `+0x64`);
- the GUI element `r4`'s vtable and first words.

The vtable is the class name. From it the constructor/initializer is findable in
the generated code, and that names the writer. Nothing is written; the fault
still happens, which is expected for this diagnostic run.

Build: SHA-256 `F328F67BD2E8DF76E0C3354BC107ED774000198E8CCE35A3D1617C0C879BA372`.
Tag: `m1-witness-044`. Texture uploads stay on to reach the fault.

## 5. What the result means

At the fault the log will carry:

```
[gui-witness] #1 sub_822358A8 r3=0 lr=82390590 r4=... ...
[gui-witness]   83496920 a=... b=... c=... d=... e=... f=... g=... h=... i=00000000
[gui-witness]   class: h=... vt=... w8=... w36=... w40=... w64=00000000
[gui-witness]   class: r4=... vt=... w0=... w4=... w8=... wC=...
```

- `vt` for `h` is the decisive value. If it lies in the guest image
  (`0x82xxxxxx`), the vtable's constructor is found by searching the generated
  code for that address; if it is a heap pointer, its content still names the
  virtual functions.
- `w8/w36/w40` confirm the page layout the consumer uses; `w64` must be 0.
- Then the `+0x64` writer is fixed and run 045 confirms.

If the fault does not happen, return the log anyway and say how long it ran; a
missing fault is itself a result.
