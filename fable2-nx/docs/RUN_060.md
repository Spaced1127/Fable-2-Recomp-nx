# run-060 - retire GPU resources by age (the no-wait race), and arm the witness

## 1. What run 059 actually showed

**There is no new crash block.** `docs/runs/059/rex_crash.log` is byte-identical
to `docs/runs/058/rex_crash.log` - same length (69110), same SHA-256
`98A1A23DBF495220FE0C707846C060EECE5F1C9D4EBB5CDBB35FFA78A6EC7618`. The 9 s
death wrote nothing, which puts it in the same class as run 041: a **below-guest
death** (host fault / OS kill) that never reaches the SDK reporter - not a guest
violation.

The log also shows the display work paid off before it died:

```
23:06:21.8xx [delete] ... (first presents)
23:06:29.389 [present] #183 slot=2 branch=1 guest#182 age=1 since_refresh=0ms 1280x720
23:06:29.471 <last line: a gui_textures.bnk read>
```

**183 presents with `age=1` and `guest#` tracking them**: the swapchain was
following the guest frames at roughly 23 Hz (the guest's own frame pacing), i.e.
the fence removal did what it was for. What changed is that presents went from
about 0.5 to 25 per second.

## 2. Why that killed it - and the design that fixes it

A deko3d command list is read by the GPU **from the memblock it was recorded
into**. Until run 058 the old waits (2 s per present copy, 250 ms per render
list) accidentally kept that memory untouched for seconds. Run 059 removed them,
so both command memories are now rewritten while the GPU may still be reading
them:

| memory | before run 059 | run 059 | consequence |
|---|---|---|---|
| present-copy command list (per present) | 3 slots, keyed by swapchain image, effectively reused every 2 s | 3 slots reused every ~0.12 s | GPU reads a list being rewritten |
| master frame command memory (2 MB) | one block, reused each frame with a 250 ms wait between | one block, reused each frame with **no** wait | same, once per frame |
| texture staging | never freed (fence poll never succeeded) | never freed | safe, but capped at 64 uploads |

**Fix: retire by AGE, never by a wait.** Every submit now bumps a global epoch
(`NoteGpuSubmit`), so:

- the master frame command memory has **3 slots** and is rotated - a block is
  rewritten only after two further frames have been submitted behind it
  (`kCommandSlots = 3`);
- the present-copy command memory has **16 slots** and is rotated per present
  instead of per swapchain image - a slot is retired after roughly half a second
  at 30 Hz;
- texture staging blocks are retired after **8 submits** (or immediately if the
  fence ever does signal), instead of never.

Queue order is the guarantee: the copy and everything that reads a block were
submitted earlier, so once several later submits have passed, that work has
executed. Nothing in this path waits on a fence any more.

## 3. The witness: armed, and now self-announcing

Run 059's log had no `[vm-lookup]` line. The hook was in the binary (strong
symbol `0x48F8240`), but the process died at 9 s and the name-table lookup that
matters first runs when the GUI batch is built (~22-50 s in earlier runs). So the
hook was not broken, just never reached.

Two changes:

- the port now logs `[fable2] probes armed: vm-null fetch, vm-invoke, name-table
  lookup (0x82C64018), per-present telemetry` at startup, so a log without it
  means a stale binary, and a log with it but no `[vm-lookup]` means the lookup
  genuinely did not happen before the death;
- each lookup line now also dumps the found object's first four words
  (`obj=… w=[…]`), so a real object can be told from a stub. The table's *size*
  is not reachable from this entry point without more RE, so the population
  question is answered by the pattern: several keys found + this one zero = a
  registration bug; every key zero = the mount never ran.
