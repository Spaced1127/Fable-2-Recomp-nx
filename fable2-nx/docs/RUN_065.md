# run-065 - deterministic discriminators for the copy chain

## 1. What run 064 proved, and what it left open

```
[upload-validate] MISMATCH via own fence: 8 samples differ (first at byte 0):
                  src=5A rb=00; checksum 08D4A082; first pixels [00000000 ...]
```

The chain writes **nothing**. But three different failures produce zeros, so this
does not yet name the guilty primitive:

1. the list never executes,
2. `buffer -> image` is a no-op,
3. `image -> image` (the present blit) is a no-op,
4. or the `image -> buffer` readback itself is the no-op (then everything upstream
   could be fine and we would still read zeros).

Run 064 also settled two things worth keeping: **fences work** (the copy and
staging fences miss only the first poll, then signal - the ring/lifetime question
is closed), and **memory is not the cause** of the ~9 s death (heap 2277 MiB free
after GPU setup, 1058 MiB untouched through the uploads).

## 2. What this build does (one run, no guessing)

Every step carries **known content on both sides**, gets its own command list, its
own fence and a bounded 250 ms wait, and is read back and logged separately:

| step | source | destination | readback tells you |
|------|--------|-------------|--------------------|
| **a** | `0x5A` buffer | `0xAA` buffer | `5A` = buffer copies execute at all; `AA` = **the 2D engine never executes** |
| **b** | `0x5A` buffer | 64x64 RGBA8 image (`Usage2DEngine`) | readback buffer is **pre-filled `0xAA`**: still `AA` = the `image -> buffer` copy did not execute (or targeted another block); `5A` = the texture-upload primitive works |
| **c** | image A (`5A` inside) | image B **pre-cleared `0xC3`** (presenter flags) | `C3` = the blit wrote nothing (**the white screen**); `5A` = the present blit works; neither = the readback path itself is broken |
| **d** | `0x5A` buffer | **presenter-shaped** image (`Render\|2DEngine\|HwCompression`) | flagged: a swapchain-like image may simply not be readable as a copy source, so a zero here is *inconclusive* |

Every image logs its **creation flags, size and alignment**, and the copy logs
`rowLength` (bytes) and `imageHeight` (rows) - one mismatch on one image is enough
to no-op the whole chain, and it will be visible next to the verdict.

Output shape:

```
[copy-diag] a buffer->buffer: pre=AAAAAAAA post=[5A5A5A5A 5A5A5A5A] PASS
[copy-diag] b image A: flags 0x800 size NNN align NN, copy rowLength 4096 bytes imageHeight 64 rows, readback pre=[AAAAAAAA AAAAAAAA]
[copy-diag] b buffer->image->buffer: post=[5A5A...] PASS (image holds the pattern)
[copy-diag] c image->image (present blit): B flags 0xD04, readback post=[C3C3...] FAIL: B still holds its 0xC3 clear - the blit wrote nothing
[copy-diag] d buffer->presenter-image->buffer (FLAGGED ...): post=[...] inconclusive/fail
[copy-diag] summary: a(...)=PASS b(...)=FAIL c(...)=FAIL d(...)=inconclusive
```

The diagnostic runs **once**, at the first real texture upload (not at boot), and
the only waits are bounded 250 ms fences around its own lists.

## 3. How to read it

- **a FAIL** -> the 2D engine never executes on this port: no copy can work, and
  the display/upload work has to move to a shader-based path. Everything else is
  moot.
- **a PASS, b FAIL (readback still `AA`)** -> the texture-upload primitive is the
  break; `rowLength`/`imageHeight` are already logged beside it, and the next
  variable is the destination image's flags (a `Usage2DEngine`-only image vs the
  presenter's `Render|H2D|HwCompression` - step d tests exactly that).
- **a+b PASS, c FAIL (`C3`)** -> the texture upload is fine and **the present blit
  is the white screen**: the swapchain image keeps its clear colour.
- **b PASS, c PASS, d FAIL** -> only swapchain-shaped images are unreadable, which
  is expected and harmless.
