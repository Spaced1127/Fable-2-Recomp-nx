# run-061 - the copy itself was invalid: DkCopyBuf units

## 1. What run 060 showed - and what the white screen actually is

The display path works: presents ran `#1..#7` at ~50-100 ms with
`branch=1 guest#N age=1 since_refresh=0-3ms`, no `giving up on render recording`.
Then the process died at ~10 s on a `gui_textures.bnk` read, with **no guest
violation and no new crash block** (`rex_crash.log` unchanged, `98A1A23D...`).

The screen was white for those 10 s. That is **not** evidence that the blit fails -
the log says why it is white:

```
frame 0 drew 0, skipped 24 (no_rasterization x24)
first color clear: value 0xFFFFFFFF, 1280x720 ...
frame 1..127 drew 0, skipped 25 (no_render_targets x24, primitive_type x1)
```

- Every frame drew **zero** primitives. The only geometry in a menu frame is one
  rectangle list (`primitive_type`), which deko3d cannot draw yet - that is M2's
  known gap - and 24 draws that are genuinely empty (Xenia skips them too).
- The guest clears its render target to `0xFFFFFFFF`, so the target really is
  white, and the presenter shows it faithfully.
- The present blit is `dkCmdBufCopyImage` (image -> image) with **no `DkCopyBuf`
  at all**, so the upload units cannot affect it. Proof of that path is now part
  of the boot validation (stage 2 below).

So there are still two separate defects: the upload copy's units (fatal, fixed
here) and no drawable geometry (M2, unchanged). A white screen stopped being a
display bug the moment the presents started following the guest.

## 2. The bug: `DkCopyBuf.imageHeight` is a ROW COUNT, not a byte count

`DkCopyBuf` is Vulkan's `VkBufferImageCopy` buffer pair: `rowLength` is **bytes
per row**, `imageHeight` is the **number of rows** in the padded source (both `0`
means "tightly packed" - which is what deko3d's own examples pass). The port was
passing the **total byte size**:

| upload | rowLength (ok) | imageHeight (wrong) | correct |
|---|---|---|---|
| 64x64 probe | 4096 | 262,144 | 64 |
| 960x720 menu texture | 4096 | 2,949,120 | 720 |

So the 2D engine was told to walk 2.9 million rows of 4096 bytes out of a 2.8 MB
block. That is invalid from the first row past the block: an invalid DMA, which
faults the GPU and kills the process at the driver/kernel level - exactly a
below-guest death with no SDK report. It also explains why every earlier "copy
verdict" was meaningless: the fence test (runs 056-058) could only see whether a
fence signalled, and no variant ever actually completed a valid copy.

**Fixed**: `source_buffer.imageHeight = blocks_high` (the row count). The padded
pitch stays `rowLength = source_pitch`.

## 3. Validation: ordered, in a clean process, with the destination read back

Two questions, answered in one boot sequence **before the guest submits anything**
and in this order, because order is what makes the fence answer meaningful (a
wedged 2D engine makes every later submission, even an empty one, never complete):

| step | submission | proves |
|------|-----------|--------|
| 0 | **empty list + `signalFence`, wait 250 ms** | whether `dkFenceWait` works at all in a clean process |
| 1 | clear into a real render target + fence | whether the 2D engine is executing at all |
| 2 | staging -> image A (`copyBufferToImage`, units fixed) -> image B (`copyImage`, the presenter's API) -> `copyImageToBuffer` -> `waitIdle` -> byte compare | whether the copies land pixels |

```
[gpu-validate] step0 empty-list fence: PASS|TIMEOUT in N ms
[gpu-validate] step1 clear+fence: PASS|TIMEOUT in N ms
[upload-validate] submitting 64x64 chain: staging -> image A (upload) -> image B (present blit) -> readback
[upload-validate] PASS: 64x64 RGBA8 chain is byte-identical ... (fences: step0 X, step1 Y)
```

How to read it:

- **step0 PASS** -> fences work here; the port's "fences never signal" note was
  wrong (the earlier `fence-only` timed out *after* the process had already run
  other GPU work). The build then uses a bounded fence wait for staging
  retirement (`fences_signalled_`), with age only as the fallback.
- **step0 TIMEOUT but step1 PASS** -> fences are broken for the signal path while
  the engine still executes: keep age-based retirement and never wait.
- **step0 and step1 both TIMEOUT, step2 MISMATCH/PASS** -> the queue is not
  completing our lists at all; the copies are then judged by the *readback bytes*
  alone, which is exactly why stage 3 reads the destination instead of trusting a
  signal.

The units under test are `rowLength = 4096` **bytes** per row and
`imageHeight = 64` **rows** (was 262,144 = total bytes). `PASS` means the upload
*and* the present blit both land pixels; `MISMATCH ... src=5A rb=00` means the
chain executed but nothing landed; any other `rb` value means addressing/pitch.

## 4. Witness: heartbeat instead of hope

The name-table hook at `0x82C64018` produced no line again, and the log could not
say whether it was unarmed or unreached (the GUI batch runs at ~22-50 s; the run
died at 10 s). The accessor hook - which fires thousands of times from boot - now
heartbeats the counter:

```
[vm-fetch] heartbeat #4096: name-table lookups so far = 0
```

So the next log answers it directly: `= 0` means the lookup never ran before the
death (look elsewhere, later), `> 0` means it ran and `[vm-lookup]` lines are in
the log.

## Reading the result

- `[upload-validate] PASS` -> the shape is right; the 10 s death had another
  cause and the log's last lines say where.
- `MISMATCH` -> the copy executes but the addressing is still off; the first
  differing byte and the src/rb values say in which direction.
- Death right after `[upload-validate] submitting` -> the shape is still invalid
  (GPU fault), and the unit table in section 2 is the place to look next.
- Alive past 60 s with `[present] ... age=0/1` flowing and texture uploads
  continuing -> the display work is done for this milestone; the remaining item is
  the guest entity crash (~48 s), and `[vm-fetch] heartbeat` says whether the
  name-table witness fired.
