appeared once at 16:09:58.425 with `self=404BC8A0`, while `[gui-upd]` (the

manager `[self+4]`, the fault chain `n24=[self+0x24]`, `h2=[n24+4]`, the loop
byte, and the live `r3` plus `[r3+36]`. Both markers are read-only; the
existing witness / `[gui-upd]` / `[gui-pass]` / `[gui-writer]` hooks and the

## Reading the result

- `[gui-mark] pass ... self=42220210 ... w36=40531DC8` **before** the
  `[gui-upd]` line: the update did reach the pass path; the missing writer is
  inside `sub_825F3050` (lookup/writer gate), not a skipped branch.
- Only `[gui-mark] wait ...` repeating, with no `pass` for `self=42220210`: the
  update is stuck in the wait loop on the `0x834BE654` byte. The logged
  `loop=` value and the iteration count name the condition.
- `[gui-mark] pass` fires but no `[gui-pass]` within the same update: the
  block is in the virtual call at `0x8233F030` before the pass call.
- `n24`/`h2` in the marker lines must match the witness (`n24=40531DC8`,
  `h2=42538C10`); if they differ, the update and the draw diverge at `+0x24`.
- `w36=` at the marker vs. `[gui-state]`: a state change between the marker
  and the draw identifies the gate that skips the writer.
