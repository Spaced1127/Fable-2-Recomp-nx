(`[gui-upd]`), while the draw faults on `42538C10`, which is reached from the
same chain as `[ [42220210+0x24] + 4 ]`. The faulting instance is never updated.

This build logs:
- `[gui-upd] self ... w36 idB4 +64 n24 h2 h2+64`: the update target's `+36`
  state, its `+0xB4` component/player ID, its `+0x64`, and the two hops
  `n24 = [self+0x24]`, `h2 = [n24+4]` with `h2+0x64`;
- `[gui-pass] self`: entry of the update pass `sub_825F3050`, proving whether the
  pass runs for the instance `sub_8233EEE0` got;
- the existing `[gui-state]`, `[gui-lookup]`, `[gui-writer]` and witness lines.

## Reading the result

- If `[gui-upd] ... h2=42538C10` and `h2+64=00000000`: the updated instance and
  the faulting one are linked; the pass `[gui-pass]` either runs (and still does
  not reach the writer) or never runs. `[gui-pass]` present = the writer/call
  path; absent = the update pass is skipped inside `sub_8233EEE0`.
- `[gui-upd] idB4=` for `42220210` vs the witness: compare with the
  `[gui-lookup]` results to see which player slot each instance belongs to.
- If `h2` is not `42538C10`, the draw's chain and the update's chain diverge at
  `+0x24`; that divergence is the bug to trace next.
- `[gui-writer]` appearing: note self and `+64`; the write path works and the
  remaining issue is ordering.
