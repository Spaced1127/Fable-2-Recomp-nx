# run-067 - bisect copy vs sample, with a real image and the real pitch

## 1. What run 066 changed

Uploads **now reach the frame list** and therefore execute:

```
[upload] #1 960x720 format 23 -> deko 45 (2949120 bytes staging, tiled 1, 1 layers)
[upload] #1 960x720 recorded into the FRAME list (rowLength 4096 bytes, imageHeight 720 rows)
[upload] #2 480x360, #3 #4 240x180 ...
present #182 15:33:31.118 -> #183 15:33:31.488 (370 ms frame, ~35 ms cadence)
death at 15:33:31.543, ~55 ms after #183
```

So the copy executes and the process dies within ~250 ms of the first real upload.
Runs 042-048 survived 40+ s precisely because uploads were skipped, so the
correlation now has two candidate mechanisms: **the copy overruns/corrupts the
destination**, or **the first draw that samples the uploaded image** is the killer.

## 2. This build: the bisect runs before the first frame

`deko3d_copy_bisect` (default on) runs in the texture-cache init - i.e. at
command-processor setup, before any guest frame - with the **real** upload #1
parameters: 960x720, RGBA8 (xenos format 23 -> deko 45), `Usage2DEngine`, one mip,
tiled, source pitch 4096 bytes, imageHeight 720 rows.

Two destinations, same source, one after the other:

| attempt | flags | what it answers |
|---|---|---|
| `tiled (real upload #1 flags)` | `Usage2DEngine` | does the copy into a real texture image kill the process? |
| `pitch-linear` | `Usage2DEngine \| PitchLinear` | is it the **tiling/pitch** rather than the copy? deko3d's size/height gives a real pitch to compare |

Each attempt logs, **before** submitting:

```
[copy-bisect] <attempt>: flags 0x... size ... align ... (derived pitch ... bytes) |
              we pass rowLength 4096 bytes, imageHeight 720 rows, rect 960x720
[copy-bisect] <attempt>: submitting copyBufferToImage only (960x720, rowLength 4096 B, imageHeight 720 rows)
[copy-bisect] <attempt>: copy fence SIGNALLED|TIMEOUT after up to 1000 ms
[copy-bisect] <attempt>: readback fence SIGNALLED|TIMEOUT | first pixels [..] - COPY OK | something else
[copy-bisect] done: at least one destination works | NO destination worked
```

Nothing else is submitted in between, and every step prints before it acts, so if
the process dies the last line names the exact point.

**Pitch check**: deko3d exposes no block-linear pitch, so the *pitch-linear* image's
`size / height` is logged next to the `rowLength` we pass (4096). If those disagree
- e.g. the image is 3840 wide and we hand the 2D engine 4096 - the mismatch is
visible in the same line, and the pitch-linear attempt then tells us whether the
2D engine accepts the unit we use or needs the image's own pitch.

## 3. Sample test: deferred by design

The guest's own draws are the natural sample test, and they are now driven from the
draw path: the frame-path probe (a 64x64 copy back from the first uploaded image,
into a block pre-filled `0xAA`, recorded into the same frame list) is checked by
`GetBoundTexture`, so it prints on the first draw after the witness allows instead
of waiting for another upload - which is exactly what pre-empted it in run 066.

If the copy bisect passes and the process still dies at the first sampling draw,
the killer is the texture descriptor/sampler path for a tiled image, and that is
the next bisect (a 64x64 render target sampling the uploaded image).
