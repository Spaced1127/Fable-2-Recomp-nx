# run-056 - name the missing VM argument, isolate the upload wedge

Two probes, no behaviour change: the run still ends at the same fault, but the
log names both unknowns. Nothing is guarded or skipped, so nothing can mask a
result.

## 1. What run 055 actually added (parsed from the returned files)

Protocol as always: `docs/runs/055/rex_crash.log` **is** `docs/runs/054/
rex_crash.log` with one block appended (prefix byte-identical; 054
`A11477CC...` 55576 B, 055 `DBB147D7...` 58946 B). The appended block - the only
new record - is:

```
pc 0x... = imagen+0x96b688   = sub_821C95D8 + 0xD8
instruccion 0xb8606a80       = ldr w0, [x20, x0]   (x20 = guest base, x0 = 0)
far dentro de la memoria del invitado: 0x00000000
x0 0   x2 0x4F7C3A78   x12 0x69784574656b7261  x13 0x2e27657461475f74
```

`x12`/`x13` are ASCII `"arkerExi"` + `"t_Gate'."`, i.e. a script symbol name, and
`x2 = 0x4F7C3A78` is a guest-heap address - the two values in the failing
thread's registers at the fault.

`addr2line` on `port/build/fable_2.elf` maps that exact pc to
`port/generated/default/fable_2_recomp.21.cpp:370` (the host instruction
`ldr w0,[x20,x0]` is confirmed in the disassembly at that address):

```c
ctx.lr = 0x821C961C;
ProcessAndProcessAndProcess206_822281F8(ctx, base);   // VM argument fetch
ctx.r3.u64 = REX_LOAD_U32(ctx.r3.u32 + 0);            // <- faults: fetch returned NULL
```

`sub_822281F8` is a three-way wrapper around the VM accessor
`AccessElement8_82A1E620`:

```
element = AccessElement8_82A1E620(vm, index);   // {value @+0, type @+4}
type    = element->type;
if (type == 2) return element->value;
if (type == 7) return element->value + 24;
return 0;                                       // <- the NULL
```

So the argument's **VM type tag is neither 2 nor 7**: the script value passed to
this opcode is of a kind the handler cannot use (or the slot was never written).
The other record in the file (pc `imagen+0x96b268`, kept from 054, stale pc) is
the same class - same instruction, same `far`, same `x2`/`x12`/`x13`.

## 2. Probe (a) - the VM argument capture

`port/src/core/vm_null_probe.cpp` (new, in `FABLE2_SOURCES`). Two passive hooks:

- **`AccessElement8_82A1E620`** - logs `[vm-fetch] live` on its first calls
  (proves the override linked), then, for every fetch the wrapper made (guest LR
  `0x82228208`) whose tag is not 2 and not 7, dumps `[vm-null]`: vm pointer,
  **argument index**, element address, **type tag**, value word, the five slots
  around it, the VM's first twelve words, and **the characters the value points
  at** (raw and at +16, where this game's string objects keep their text). It
  also replays the last eight fetches and the last eight dispatches, so the
  crashing call can be read in context.
- **`sub_821C95D8`** - logs the first 24 dispatches (`[vm-call]`, caller LR and
  r4-r7) and keeps the last eight in a ring.

What one run names: the **argument index** (`idx=`), the **type tag**, and the
**string** - expected to contain the `...arketExit_Gate'.` text seen in the crash
registers, which identifies the script call. That is the producer to fix in
run-057. No guard: a guard here would be the fourth blind patch of this class.

Both hooks are passive: they write nothing to guest memory, keep no state the
guest can observe, and add one word read per VM element access. Cost is a few
dozen log lines plus up to 2 s per upload variant that hangs.

## 3. Probe (b) - the upload self-test (white screen)

`deko3d_upload_probe = true` in the shipped `fable_2.toml`. At texture-cache
init, before the guest submits any GPU work, five 64x64 RGBA8
`copyBufferToImage` copies run on the shared queue; each has its own image,
staging block, command list and fence, bound to 2 s:

| # | variant | the one difference |
|---|---------|--------------------|
| 1 | `control-presenter-flags` | destination created like the presenter's images (`Render\|Present\|2DEngine\|HwCompression`) |
| 2 | `baseline-2dengine` | none - today's failing path, at 64x64 |
| 3 | `staging-cpuuncached` | staging block CPU-**uncached** |
| 4 | `dest-pitchlinear` | destination pitch-linear (untiled) |
| 5 | `no-inlist-barrier` | in-list barrier removed |

The order is deliberate: a hanging copy wedges the queue for the rest of the
session, so only the variants up to the first failure can answer anything, and
the control has to run before the suspects.

## Reading the result

Expected tags, first line each:

- `[upload-probe] begin: 5 variants, 64x64 RGBA8, pitch 4096, 2000 ms bound`
- `[upload-probe] <variant>: PASS|TIMEOUT in N ms (...)` - one per variant, then
  `[upload-probe] done: P of N attempted variants completed...`
- `[vm-fetch] live #1 caller=82228208 ...` - the accessor hook is installed.
- `[vm-call] #N tid=N caller=... vm=...` - the opcode handler's dispatches.
- `[vm-null] #1 tid=... vm=... index=... elem=... type=... value=...` plus the
  slot, VM-word, value-text, fetch-ring and dispatch-ring lines.

What each result means:

**Upload**
- 1 TIMEOUT -> `copyBufferToImage` is unusable on this queue at any shape: the
  upload must move to a DKSH pass or a `copyImage` from a staging image.
- 1 PASS, 2 TIMEOUT -> the texture image creation is the difference (its flags);
  run-057 clones the presenter's flag set for texture images.
- 1+2 PASS and 3, 4 or 5 TIMEOUT -> that single variable is the culprit.
- all PASS -> 64x64 is fine; the real upload differs in size/format/pitch, and
  run-057 bisects those next.

**Crash**
- `[vm-null]` with `index=` and `type=` names the argument. `type` 0/1/3/5 means
  a nil/bool/number/string where an object was expected; a `type` that is an
  object tag but a null `value` means an unwritten slot. The value text names the
  script symbol - fix there in run-057, not at the consumer. If more than one
  `[vm-null]` fires, every one is the same defect class; the **last** one before
  the crash is the fatal one and is the one to fix.
- No `[vm-null]` line but a crash at the same pc: the failing value never came
  through the accessor (a different path), and the `[vm-call]`/dispatch ring plus
  the crash registers locate it.
- `[vm-fetch] live` missing: the override did not link; nothing else in the log
  is trustworthy for this probe, say so before spending another run.
